## 一、plocate 索引格式

`db.h` 里的 `Header` 就是全部布局：

- magic `\0plocate`，version 2
- `hash_table_offset_bytes` / `hashtable_size` / `extra_ht_slots` → trigram 哈希表（开放寻址 + 溢出槽）
- `num_docids` / `filename_index_offset_bytes` → docid 文件名区
- `zstd_dictionary_offset_bytes` → zstd 字典（**对短字符串单独训练字典，压缩率极高**）
- `directory_data_offset_bytes` + `next_zstd_dictionary_*` → **目录 mtime 区**，这就是 `updatedb` 做增量跳过用的数据（上一轮说的 mtime 方案，它的工程落地就在这）
- `check_visibility`（做权限过滤）

倒排项是 `struct Trigram { uint32_t trgm; uint32_t num_docids; uint64_t offset; }`，哈希函数是 CRC32C 风格（多项式 `0x1edc6f41`）。

**关键设计：trigram 按字节而非 Unicode 码点。**`parse_trigrams.h` 注释写得很明确：既简化表结构（等长），又防止 CJK 组合爆炸。对你来说这是好消息——中文文件名不会把索引撑爆。

## 二、查询流水线（plocate.cpp:377 起）

```
needle → parse_trigrams() 拆成 trigram 合取式
       → 哈希查表取 posting list（TurboPFor 压缩的 docid 有序表）
       → 多组求交集 → 候选 docid（注意：这是假阳性集合）
       → 按块批量 pread 读文件名区 → 解压 → 块内精确匹配 → 输出
```

**发现 1：全量扫描时它刻意不用 io_uring。**注释原文：

```371:376:/root/src-dl/plocate-1.1.15/plocate.cpp
// We do this sequentially, as it's faster than scattering
// a lot of I/O through io_uring and hoping the kernel will
// coalesce it plus readahead for us. Since we assume that
// we will primarily be CPU-bound, we'll be firing up one
// worker thread for each spare core (the last one will
// only be doing I/O). access() is still synchronous.
```

io_uring 只在**随机小 I/O** 用（查哈希表 bucket、取单个 docid 块，`plocate.cpp:128`）。顺序大块读反而用同步 `complete_pread`，理由是让内核自己合并 + 预读。

**发现 2：32 块一组批量读 + 多线程解压。**

```444:450:/root/src-dl/plocate-1.1.15/plocate.cpp
	for (uint32_t io_docid = 0; io_docid < num_blocks; io_docid += 32) {
		uint32_t last_docid = std::min(io_docid + 32, num_blocks);
		size_t io_len = offsets[last_docid] - offsets[io_docid];
		if (compressed.size() < io_len) {
			compressed.resize(io_len);
		}
		complete_pread(fd, &compressed[0], io_len, offsets[io_docid]);
```

文件名区是**每 N 个 docid 打包成一个 zstd 块**，`offsets[]` 记块边界。查询时一次连续读 32 个块的字节区间，塞进有界队列（限深 256 ≈ 2MB），N 个 worker 线程取出来解压+匹配。所以 plocate 的性能公式是：**I/O 顺序化 + 块级压缩摊销解压开销 + CPU 并行解压**（它假定自己是 CPU bound）。

**发现 4：祖先链聚合值必须冒泡更新。**新增条目后，它先把从 `watched_entry` 到根的所有祖先以 `ENTRY_DELETED + FLAG_SIZE` 广播一次（把它们从"按 size 排序的索引"里摘出来），插入完成后再广播 `ENTRY_CREATED` 让它们按新 size 重新入位。这是很容易被自己实现时漏掉的一点：**目录的 size / 子项数是聚合值，任何增删改都要沿父链冒泡刷新。**

**发现 5：事件合并与跳过。**`get_skippable_events()` 判断：如果某事件路径是被删目录的后代（严格前缀 + `/`，避免 `/ab` 误匹配 `/abc`），直接跳过——`rm -rf` 一棵大树时省掉上万次无意义处理。事件走 `GAsyncQueue` 批量 `process_queued_events()`，不是来一条处理一条。

另外它是**双后端抽象**：`FSEARCH_FOLDER_MONITOR_FANOTIFY` / `_INOTIFY` 通过 `event->monitor_kind` 分派，fanotify 拿不到权限时自动降级 inotify。

## 四、对你 ext4 索引方案的修正建议

| 环节 | 抄谁 | 具体做法 |
|---|---|---|
| 全量扫描 | **plocate** | `openat`+`O_NOATIME`+`d_type` 免 stat+目录 mtime 跳过 |
| 扫描并发 | **两个都别抄** | 两者扫描都是单线程（fsearch 的 `io_pool` 也是 `max_threads=1`）。你自己做顶层目录分片并行 |
| 增量 | **fsearch** | fanotify + `FAN_EVENT_ON_CHILD`；新目录即扫；祖先链冒泡；事件批合并 |
| 索引结构 | **plocate 思路** | trigram 倒排（**按字节**，中文安全）+ 块级 zstd 字典压缩 + 有界队列多线程解压 |
| 查询 I/O | **plocate 哲学** | 顺序大块 pread，别迷信 io_uring；io_uring 只用于随机小 I/O |
| 存储 | **自己写** | 两个都不满足你要的 size/mtime；SQLite FTS5 trigram 最省事，但要做块级压缩得自研 |

## 整体是两遍扫描

字典随后在 `database-builder.cpp:544` 以 level 6 编译成 `ZSTD_CDict`。**对短字符串（文件名）单独训练字典，是它索引体积小的关键。**

**第二遍** — 真正入库、生成 trigram、压缩写盘。

## 五个核心设计

### 1. docid 是块号，不是文件号

```303:303:/root/src-dl/plocate-1.1.15/database-builder.cpp
	uint32_t docid = num_blocks;
```

一块含 32 个文件名。所以命中一个 docid = 命中一整个块，必须解压整块再在块内精匹配。**这是整套设计的核心权衡：用"块级假阳性"换顺序 I/O 和摊销解压。**

### 2. trigram 生成：4 字节读取 + 逐字节滑动

```326:329:/root/src-dl/plocate-1.1.15/database-builder.cpp
			memcpy(&trgm, ptr, sizeof(trgm));
			++ptr;
			trgm = le32toh(trgm);
			add_docid(trgm & 0xffffff, docid);
```

一次 `memcpy` 读 4 字节取低 3 字节，靠"末尾必有 `\0`"安全多读一字节；指针逐字节推进产生重叠 trigram。判断终止用的是 `trgm <= 0xffffff`（说明第 4 字节是 0）。

**副作用：短于 3 字节的文件名不产生任何 trigram** —— 这类文件无法用倒排检索，只能走全量扫描。这正是 `scan_all_docids()` 存在的理由，也解释了为什么搜索 1~2 字符的关键词时 plocate 会退化成全扫。

### 3. 倒排表：delta-1 + PForDelta 128 分组

```56:70:/root/src-dl/plocate-1.1.15/database-builder.cpp
void PostingListBuilder::add_docid(uint32_t docid)
{
	// Deduplicate against the last inserted value, if any.
	if (docid == last_docid) {
		return;
	}

	pending_deltas.push_back(docid - last_docid - 1);
	last_docid = docid;
	if (pending_deltas.size() == 128) {
		append_block();
		pending_deltas.clear();
		num_docids += 128;
	}
}
```

差值减 1（delta-1）保证非负。凑满 128 个就编码一块，**满块用交错布局**（SIMD 友好），尾部不足 128 的用非交错：

```96:102:/root/src-dl/plocate-1.1.15/database-builder.cpp

{

	assert(pending_deltas.size() == 128);
	unsigned char *end = encode_pfor_single_block<128>(pending_deltas.data(), 128, /*interleaved=*/true, buf);
	encoded.insert(encoded.end(), buf, end);
}
```

首值单独 `write_baseval()` 存为基准。TurboPFor 是它自己重写的（注释说约官方实现 80% 性能，但不依赖 SSE4.1/AVX，可移植）。

### 4. 块压缩与偏移表

### 5. 哈希表：素数 + Robin Hood 探测

# 第二块：fsearch 结构化过滤（`fsearch_query_matchers.c` + sort）

## 结论先说：它的过滤是 O(n) 全扫，没有任何索引加速

matcher 是统一签名的函数指针：`(FsearchQueryNode *node, FsearchQueryMatchData *match_data) -> uint32_t`。所有数值类属性共用一套比较器：

```45:61:/root/src-dl/fsearch/src/fsearch_query_matchers.c
cmp_num(int64_t num, FsearchQueryNode *node) {
    switch (node->comparison_type) {
    case FSEARCH_QUERY_NODE_COMPARISON_EQUAL:
        return num == node->num_start;
    case FSEARCH_QUERY_NODE_COMPARISON_GREATER:
        return num > node->num_start;
    case FSEARCH_QUERY_NODE_COMPARISON_SMALLER:
        return num < node->num_start;
    case FSEARCH_QUERY_NODE_COMPARISON_GREATER_EQ:
        return num >= node->num_start;
    case FSEARCH_QUERY_NODE_COMPARISON_SMALLER_EQ:
        return num <= node->num_start;
    case FSEARCH_QUERY_NODE_COMPARISON_RANGE:
        return node->num_start <= num && num < node->num_end;
```

`size` / `date_modified` / `depth` / `childcount` 全是同一个套路：取 entry 的属性值 → `cmp_num`：

```115:122:/root/src-dl/fsearch/src/fsearch_query_matchers.c
fsearch_query_matcher_size(FsearchQueryNode *node, FsearchQueryMatchData *match_data) {
    FsearchDatabaseEntry *entry = fsearch_query_match_data_get_entry(match_data);
    if (entry) {
        const int64_t size = db_entry_get_size(entry);
        return cmp_num(size, node);
    }
    return 0;
}
```

**全部是逐 entry 调用**。我在 `fsearch_database_index.c` 里看到三处 "size sorted indexes" 的注释，但搜遍代码没有对应的排序索引结构——那应该是历史遗留注释。

## 排序只服务于结果展示，不是过滤

`fsearch_database_search_view.c:216` 的 `fsearch_database_search_view_sort()` 是对**已过滤出的结果集**排序；`get_idx_for_sort_type()` 只做升序/降序的下标映射。而 `fsearch_database_sort.c` 里那串 `chain.properties[]` 是**多级比较链**（比如按 size 排序时，size 相同再比 name、再比 path），是 comparator 定义，不是索引。

所以：

| | 名字子串搜索 | 结构化过滤（size/dm/childcount） |
|---|---|---|
| plocate | trigram 倒排，**O(候选)** | 不支持 |
| fsearch | 内存数组遍历 + strstr/regex，**O(n)** | **O(n) 全扫** |

两个项目在结构化过滤上都是暴力的。fsearch 之所以体感快，靠的是**全部条目常驻内存 + C 实现 + 无磁盘 I/O**，不是算法。

# 对你实现的直接结论

1. **名字检索照抄 plocate**：32 文件/块 + zstd 字典 + trigram 倒排（delta-1 + PForDelta 128）+ Robin Hood 哈希表。这套是现成验证过的。
2. **务必留全量扫描兜底路径**：短于 3 字节的名字没法建 trigram，短关键词查询必然退化。
3. **结构化过滤要自己加索引**，两个项目都给不了。三个选项：
   - **排序数组**：每个数值属性存一份按值排序的 docid 数组，范围查询二分定界 → O(log n + k)。代价是插入/删除要 O(n) 搬移（索引是批量重建的场景下可接受，实时增量场景不行）
   - **B+ 树 / LSM**：适合有实时增量，工程量大
   - **位图索引 + RoaringBitmap**：对 size 分桶、mtime 分桶，每桶一个位图，过滤靠位图 AND/OR。读多写少场景最省事，且位图压缩率高，还能和 trigram 倒排的候选集直接做 AND

# 一、TurboPFor：倒排表压缩

## 块头一个字节定类型

```377:389:/root/src-dl/plocate-1.1.15/turbopfor-encode.h
unsigned char *encode_pfor_single_block(const Docid *in, unsigned num, bool interleaved, unsigned char *out)
{
	assert(num > 0);
	if (interleaved) {
		assert(num == BlockSize);
	}

	unsigned bit_width, exception_bit_width;
	BlockType block_type = decide_block_type(in, num, &bit_width, &exception_bit_width);
	*out++ = (block_type << 6) | bit_width;
```

首字节：低 6 位 = bit width，高 2 位 = 块类型。四种类型（`turbopfor-common.h`）：

| 类型 | 适用 | 布局 |
|---|---|---|
| `CONSTANT` | 128 个 delta 全相同 | 直接存那一个值 |
| `FOR` | 无异常值 | bit width(6b)+type(2b) → 128 个定宽值 |
| `PFOR_BITMAP` | 异常值多 | + 异常位宽(8b) + 位图 + 异常值 + 基值 |
| `PFOR_VB` | 异常值少 | + 异常个数(8b) + 基值 + varbyte 异常值 + 异常下标 |

`PFOR_BITMAP` 的完整布局（源码注释）：

```491:497:/root/src-dl/plocate-1.1.15/turbopfor.cpp
// PFor block with bitmap exceptions. Layout:
//
//  - Bit width (6 bits) | type << 6
//  - Exception bit width (8 bits)
//  - Bitmap of which values have exceptions (<num> bits, rounded up to a byte)
//  - Exceptions (<num_exc> values of <bits_exc> bits, rounded up to a byte)
//  - Base values (<num> values of <bits> bits, rounded up to a byte)
```

## 核心思想：定宽 + 异常值

一个 block 里 128 个 delta，如果取最大值的位宽 `max_bits`，小值会浪费空间。PFor 的做法是选一个小一点的 `bit_width`，超过它的值**只存低位部分，高位溢出部分单独存为异常值**。判断异常就是一行：

```207:207:/root/src-dl/plocate-1.1.15/turbopfor-encode.h
			bs.write((in[i] >> bit_width) != 0);
```

## 位宽选择：直方图 + 成本模型（不是固定阈值）

`decide_block_type()` 先判 CONSTANT，再建位宽直方图，然后**枚举所有候选位宽算字节成本取最小**：

```292:312:/root/src-dl/plocate-1.1.15/turbopfor-encode.h
	// Straight-up FOR.
	unsigned best_cost = bytes_for_packed_bits(num, max_bits);
	unsigned best_bit_width = max_bits;

	// Try PFOR with bitmap exceptions.
	const unsigned bitmap_cost = bytes_for_packed_bits(num, 1);
	unsigned num_exceptions = 0;
	for (unsigned exception_bit_width = 1; exception_bit_width <= max_bits; ++exception_bit_width) {
		unsigned test_bit_width = max_bits - exception_bit_width;
		num_exceptions += histogram[test_bit_width + 1];

		// 1 byte for signaling exception bit width, then the bitmap,
		// then the base values, then the exceptions.
		unsigned cost = 1 + bitmap_cost + bytes_for_packed_bits(num, test_bit_width) +
			bytes_for_packed_bits(num_exceptions, exception_bit_width);
```

varbyte 分支的成本是**估算**的（用累计直方图按 varbyte 长度分档），注释说这个近似只影响总库体积约 0.1%。

## 交错布局（interleaved）

满块用 4 路交错写，为 SIMD 解码服务：

```170:173:/root/src-dl/plocate-1.1.15/turbopfor-encode.h
		InterleavedBitWriter<4> bs0(out + 0 * sizeof(uint32_t), bit_width);
		InterleavedBitWriter<4> bs1(out + 1 * sizeof(uint32_t), bit_width);
		InterleavedBitWriter<4> bs2(out + 2 * sizeof(uint32_t), bit_width);
		InterleavedBitWriter<4> bs3(out + 3 * sizeof(uint32_t), bit_width);
```

128 个值拆成 4 组 32 个，每组位打包后交错存放 —— 解码时能一次 SIMD 处理 4 路。尾部不足 128 的块只能走非交错（所以 `finish()` 里 `interleaved=false`）。

## 要自己实现的话

你需要的最小集其实只有三块：`write_baseval`（变长基准值）+ `encode_pfor_single_block<128>` + `decode_pfor_delta1_128`。真正的难点是**位打包的位序**（LE + 跨字节）和 **delta-1 的 off-by-one**（`prev_val = out[i] = bs.read() + prev_val + 1`）。

偷懒方案：直接用 [TurboPFor 官方库](https://github.com/powturbo/TurboPFor) 或 RoaringBitmap（Java 端若要用）。另外如果你的索引全部常驻内存、文件量不到千万级，**直接存 `uint32` 数组不压缩也完全够用** —— plocate 压缩是为了让 200MB 的库能在磁盘上快速 pread；你的场景如果是内存常驻，压缩反而拖慢查询。

## 索引层的具体设计（结合前几轮结论）

**必须做成的两个 O(1)/O(log n) 查询：**

1. **`parent:"<path>"` → 该目录的直接子项**。这是浏览时每次点目录都触发的，绝不能全扫。做法：
   - 每个目录分配 `dir_id`，每个条目存 `parent_id`
   - 维护 `dir_id → [child_entry_id...]` 的索引（哈希表或每个目录一个小数组）
   - **注意：fsearch 没做这个**（只有 parent 指针），因为它是桌面单次全量场景；你是交互式浏览，必须做
   - 路径字符串 → dir_id 的映射另建一个哈希表（`"/mnt/data/foo" → 42`），避免每次解析路径

2. **名字子串 / 通配**。否则搜索框会卡：
   - 简单版：内存数组 + 逐条 `strcasestr`（百万级条目约几十 ms，可接受）
   - 进阶版：抄 plocate 的 trigram 倒排（32 文件/块 + zstd + PForDelta）
   - **建议先用简单版**，等文件量过百万再上倒排

**其余都可以 O(n)**：排序、类型过滤、翻页都是在结果集上做。

**扫描与增量**（前面结论）：`getdents64` + `d_type` 免 stat + `openat` 相对路径 + 目录 mtime 跳过；有 root 加 fanotify `FAN_EVENT_ON_CHILD`。
